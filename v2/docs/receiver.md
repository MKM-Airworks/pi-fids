# 端末専用受信サービス（初期実装）

管理側から公開便・画面指示・必要画像を取得し、端末内のSQLiteへ保存する。Kioskは端末内localhostを表示するため、Edgeの一時セッションを終了しても、受信サービスの保存は残る。編集APIは403、管理画面は404となる。

```sh
cd v2
python3 -m pifids.receiver --source http://127.0.0.1:8800 --airport ROR --display-id gate-01 --port 8801
```

表示URL：`http://127.0.0.1:8801/display?airport=ROR&displayId=gate-01&kiosk=1`

WindowsのKiosk起動は `Start-PiFidsKiosk.ps1 -Airport ROR -DisplayId gate-01 -Port 8801` とする。受信サービスの先行起動が必要。標準保存先は `~/.pifids-v2/receiver.sqlite`。端末・画面を別プロセスで試す場合は `--database` と `--port` を分ける。

必要画像をSHA-256で確認して保存した後、公開便・画面指示を同じDBトランザクションで反映する。取得・検証失敗時は公開表示を置き換えない。保存済みより古い版も拒否する。配信元の下書きは保存しない。通信停止中も受信サービスを起動でき、保存済みの画像と公開表示を配信する。未受信の初回起動には公開情報がない。

## 確認と残作業

Macで管理サーバーからの受信・画像表示、管理サーバー停止中の受信サービス再起動・画面再表示を確認。保存の再読込、画像整合性失敗、古い版、空港の取り違えによる更新拒否も自動テストで確認。

これはV2試作の受信プロトコル。MKM Flight Webの既存APIは変更・利用していない。認証付きLAN配信、正本切替・epoch、単一リリースによる便と指示の取得一貫性、同期状況の管理PCへの報告、画像キャッシュ整理、サービス登録・自動起動・異常終了復帰、Windows/Pi実機検証は未実装。現在は空港ごと30画像の保存上限がある。管理サービスはlocalhost限定のため、同一Mac上での試験まで。

航空会社の実ロゴ・画面サンプルは後日受領し、今回の受信保存とは独立して表示テンプレートへ反映する。
